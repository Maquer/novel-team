## 二、架构设计

### 2.1 整体流程

```
导入小说 → 拆书（提取剧情人物关系）→ 生成剧情纲要
    ↓
输入用户意见
    ↓
检索相关正文片段和剧情纲要
    ↓
对正文片段进行修改
    ↓
同步更新剧情纲要
```

### 2.2 三阶段创作

| 阶段 | 功能 | 字数控制 |
|------|------|---------|
| **创作章节** | 生成大纲式章节（200字/章）| 快速生成，50+线程并行 |
| **创作剧情** | 扩充剧情细节（1k字/章）| 中等粒度 |
| **创作正文** | 润色文本和描写（2k字/章）| 最终精修 |

**示例计算**：
- 创作50章 × 200字 = 10,000字
- 扩充到1k字/章 = 50,000字
- 再扩充到2k字/章 = 100,000字（十万字）

### 2.3 技术栈

```
Python + Gradio (UI) + FastAPI (后端)
├── LLM API: GPT / 文心一言 / 豆包 / 智谱
├── RAG: 本地向量检索
├── 多线程: 并行生成
└── MongoDB: 可选存储
```

### 3.3 Prompt 设计特点

**上下文注入模式**（用于Prompt Caching）：
```yaml
# context_prompt.txt
user:
下面是**小说简介**。
**小说简介**
{summary}

assistant:
收到，我会参考小说简介进行创作。

user:
下面是**章节上下文**，用于在创作时进行参考。
**章节上下文**
{context_y}

assistant:
收到，我在创作时需要考虑到和前后章节的连贯。

user:
下面是**章节**，需要你重新创作的部分。
**章节**
{y}

assistant:
收到，这部分章节我会重新创作。
```

**审阅Prompt**：
```yaml
system:
现在你是一个网文主编，正在审稿。
在审稿时，由于作者只提交了一个正文片段，所以只评判该片段的格式、文笔、画面感，不评判结构和情节。

考虑角度：
1. 场景描写是否够具体？是否有画面感。
2. 人物刻画如何？是否有外貌、动作、心理、语言等细节描写。
```

## 五、关键发现

### 5.1 渐进式创作哲学

Long-Novel-GPT的核心理念是"自上而下扩写"：
1. 先写粗略大纲（100-200字）
2. 再扩充剧情细节（500-1000字）
3. 最后润色正文（1500-2000字）

每阶段只关注一个粒度，避免一次性生成过长导致质量下降。

### 5.2 上下文智能管理

- 自动切分章节为chunk（默认1000字）
- 自动加入前后章节作为上下文
- 自动计算并控制API调用费用
- 多窗口并行生成，互不干扰

### 5.3 Prompt Caching优化

采用多轮对话模式，每轮注入一个信息块：
- 第1轮：小说简介
- 第2轮：章节上下文
- 第3轮：当前章节
- 第4轮：创作指令

这种设计可以利用LLM的Prompt Caching功能，降低Token成本。

### 5.4 审阅机制

内置网文主编人设，从三个角度审阅：
1. 场景描写是否具体、有画面感
2. 人物刻画是否细致（外貌/动作/心理/语言）
3. 其他文笔问题
