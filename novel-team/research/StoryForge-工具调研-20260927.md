## 三、技术架构

### 3.1 技术栈

```
React + TypeScript + Vite
├── IndexedDB（本地存储）
├── TipTap（富文本编辑器）
├── Tailwind CSS（样式）
├── Playwright（E2E测试）
└── Vitest（单元测试）
```

### 3.2 核心模块

| 模块 | 文件 | 功能 |
|------|------|------|
| **Harnass** | `product-platform/production-runtime.ts` | 模型调用、版本保护、运行证据 |
| **记忆系统** | `knowledge-ledger/` | 事实账本、状态追踪、检索索引 |
| **世界引擎** | `world-node.ts`, `world-rules.ts` | 世界版本、设定封存、派生复用 |
| **长篇** | `storyline-progress.ts`, `outline.ts` | 卷纲、章纲、细纲、章节编辑 |
| **短篇** | `review-result.ts` | 全篇审校、完成检查 |
| **剧本** | `screenplay/` | 场景卡、AST表示、格式导出 |
| **漫画** | `comic/` | 分页分镜、视觉档案、排字 |
| **节点创作** | `node-flow.ts` | 可视节点连接、输入输出检查 |

### 3.3 三注册表系统

StoryForge强制收口到三个单一事实源：

1. **CONTEXT_SOURCES** + `assembleContext()`
   - AI读什么
   - 固定条数裁剪只能是最终预算保护

2. **FIELD_REGISTRY** + `AdoptionSchema` + `adopt()`
   - AI可以正式写什么
   - 候选最终写入字段

3. **PROJECT_TABLES**
   - 表的导出、导入、删除、迁移、作用域、引用重映射生命周期

**规则**：动手前依次回答：
- 入口和用户结果是什么？
- AI/代码读取哪些来源，是否已登记在CONTEXT_SOURCES？
- 候选最终写入哪些字段，是否已登记在FIELD_REGISTRY/AdoptionSchema？
- 涉及哪些表，是否由PROJECT_TABLES派生完整生命周期？
- 哪些调用方、下游、反例和真实用户路径会受影响？

## 四、长篇创作流程

### 4.1 创作环节

| 环节 | 工具 | 对作者的帮助 |
|------|------|-------------|
| 构思与资料 | 灵感反推、项目参考、文档解析 | 零散想法转创作依据 |
| 世界与背景 | 世界起源、环境、历史年表、地图 | 管理设定与空间关系 |
| 故事与人物 | 故事设计、主支线、角色生成、关系网 | 动机/冲突/情节关联 |
| 大纲与写作 | 卷纲、章纲、细纲、续写/扩写/重写/润色 | 整体规划与逐章调整 |
| 连续性管理 | 伏笔、事实库、状态表、物品栏、年表 | 跟踪变化，减少遗漏冲突 |
| 风格与控制 | 文风学习、创作规则、提示词库 | 明确写作要求，检查AI结果 |
| 保存与恢复 | 自动保存、版本历史、完整备份 | 保留作品与过程 |

### 4.2 长篇记忆系统

四层资料链，确保跨章一致性：

1. **正文**：原始证据，不可覆盖
2. **事实库**：结构化状态（人物、事件、物品）
3. **摘要**：章节/卷/全局摘要，帮助定位
4. **检索索引**：找回相关片段，核对原文指纹

**流程**：
```
生成任务 → Context Gateway → 查目录 → 按需读取细节 → 记录来源
摘要与索引核对原文指纹 → 过期或缺失时保留原文回查路径
```

### 4.3 章后整理

每章正文采纳后的确认流程：

1. **提取变化**：事实、人物状态、关系、物品、年表、伏笔、主支线
2. **未来影响分析**：已确认历史保持稳定，待调整标记为"待处理"
3. **作者决策**：如何修订后续规划

**示例**：第8章揭示信物归属，第80章又要用到它 → 检索定位前文，核对持有者/约定/时间。

## 五、与世界引擎的关系

### 5.1 派生流程

```
小说创作 → 显式派生 → 世界草稿 → 封存 → 世界版本
                                      ↓
                              互动产品读取（只读）
                              - 跑团：规则+秘密
                              - 角色聊天：人物+关系
                              - AI小镇：居民+地点
```

### 5.2 版本控制

- 世界有独立身份、来源记录、不可变版本
- 从小说派生时保存作者选定的内容范围、作品版本、内容指纹
- 不同产品按自己的需要读世界（声明必读、选读、禁止读取）
- 每次读取留Context Manifest，发布时聚合SourceManifest

## 八、关键发现

### 8.1 产品边界清晰

StoryForge严格区分：
- **Project**：LocalWorkspace壳，只保存身份指针
- **Work**：实际作品，保存标题/简介/流派/状态/字数/文风
- **World**：独立身份，可派生、封存、版本化

禁止Project镜像Work数据，禁止Work回读Project。

### 8.2 执行层治理严格

- 模型调用必须进入登记的Agent Skill/Run Contract/durable Harness
- 模型输出先成为CreativeArtifact候选，作者确认后才可adopt()
- durable run保存contract、manifest、事件、checkpoint、stale证据、repair与终态receipt

### 8.3 验证机制完整

验证按风险递增：
1. 定向测试或检查器
2. `npm run check:architecture`、`check:required-tables`、`check:ai-manual`
3. `npm run build`
4. `npm run ci`
5. `npm run ci:e2e`（UI/API/数据恢复）

## 十、风险提示

### 10.1 复杂度风险

StoryForge代码库庞大（README 44KB），架构复杂，直接移植成本高。

**建议**：仅借鉴理念，不移植代码。

### 10.2 前端依赖

StoryForge是完整的前端应用，依赖Node.js + npm + React + IndexedDB。

**建议**：不尝试在iSH运行，仅作为参考设计。

### 10.3 维护成本

StoryForge持续活跃（今天刚推送），版本迭代快，跟随成本高。

**建议**：锁定v3.9.1版本作为参考，不追求同步更新。
